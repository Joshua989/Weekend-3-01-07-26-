1. Introduction

1.1 Purpose

This document specifies the requirements of IRO (Issues Reporting Outlet), a web-based system through which AAUA students and indigenes of the host communities report issues that affect them, and through which an IRO desk officer reviews, escalates and resolves those reports. It is written for the course lecturer, the project developer, and any future team that extends the system. It describes what the system must do (functional requirements), how well it must do it (non-functional requirements), and how its major components interact.

1.2 Scope

Relations between AAUA students and the host communities (Akungba, Iwaro, Etioro, Ayegunle and Oke-Oka) are affected by disputes over rent and accommodation, security, land, cultural festivals, sanitation, transport and prices. Today these issues are reported through scattered informal channels (the SUG, community chiefs, WhatsApp groups, the police), many are never reported for fear of victimisation, and reporters rarely learn what happened to their complaint.

IRO provides a single, neutral outlet that:

  • lets any student or indigene submit an issue report, anonymously if they wish;
  • gives every report a unique ticket ID that the reporter uses to track its progress;
  • gives the IRO desk officer a dashboard to view, filter, update, escalate and close reports;
  • keeps a timestamped history of every status change for accountability.

Out of scope for version 1.0 (the mini interface): SMS/e-mail notifications, file/photo uploads, a server-side database, multiple officer accounts and Yoruba translation. These are listed as future enhancements in Appendix B.

2. Overall Description

2.1 Product Perspective

IRO is a new, self-contained web application. Version 1.0 is a static front-end (HTML, CSS, JavaScript) that runs in any modern browser and stores data in the browser's localStorage. All data access goes through a single data-layer object (IssueStore), so a later version can replace browser storage with a server API and database without changing the user interface.

2.2 Product Functions (summary)

  • Present the purpose of IRO, reporting guidelines and issue categories.
  • Capture an issue report with reporter type, category, severity, location, date, title and description.
  • Allow anonymous reporting.
  • Validate input and generate a unique ticket ID.
  • Let reporters track status and history with the ticket ID.
  • Let the desk officer log in, view statistics, search/filter reports, view details, change status with a note, escalate and delete reports.

2.3 User Classes and Characteristics

IndigeneLandlord, trader, driver, farmer, chief or other resident of the host communities. Selects their community.Low–medium; a simple, clear interface is essential.

2.4 Operating Environment

  • Client: any modern browser (Chrome, Firefox, Edge, Safari, Opera Mini excluded) on Android, iOS, Windows, macOS or Linux.
  • Server: none required for v1.0; the files can be opened locally or hosted on any static host (e.g. GitHub Pages).

2.5 Design and Implementation Constraints

  • Must be simple to build and submit within one week (course deadline).
  • Plain HTML5, CSS3 and JavaScript (ES6); no frameworks or build tools.
  • Data in v1.0 is held in the browser, so reports are visible only on the device where they were made.
  • Must respect the confidentiality of reporters in line with the NDPA 2023.

2.6 Assumptions and Dependencies

  • Users have access to a browser with JavaScript enabled.
  • The university and community leaders agree to act on escalated reports.
  • A production deployment will add a server-side database and proper authentication.

3.3 Key Interaction Sequences

(a) Submitting a report. Reporter opens report.html → selects reporter type (ReportForm shows matric field for students or community field for indigenes) → fills the form → ReportForm.validate() checks every field → IssueStore.create() builds the issue object, generates a ticket ID, sets status Submitted, adds the first history entry and saves to storage → ReportForm displays the ticket ID and a "Track this report" link.

(b) Tracking a report. Reporter enters the ticket ID on track.html (or follows the link) → Tracker calls IssueStore.findById() → if found, the title, category, severity, current status and full history are shown; otherwise an error message is shown. Name, contact and description are never shown on this page.

(c) Managing a report. Desk officer logs in on admin.html → AdminDesk loads IssueStore.stats() and IssueStore.getAll() → officer searches/filters and opens a report → officer chooses a new status (Under Review, Escalated, Resolved, Closed) and writes a note → IssueStore.updateStatus() records the change with a timestamp → the reporter sees the new status and note the next time they track the ticket. Choosing Escalated means the officer forwards the case to the relevant authority.

4. Functional Requirements

Priority: H = must have (in v1.0), M = should have, L = could have (future).

IDRequirementDescriptionPri.
4.1 Public information
FR-01Home pageThe system shall display the purpose of IRO, the four-step reporting process, the list of issue categories and an emergency notice.H
FR-02NavigationEvery page shall have a navigation bar linking Home, Report an Issue, Track Report and Admin.H
4.2 Issue reporting
FR-03Reporter typeThe system shall require the reporter to choose Student, Indigene or Other.H
FR-04Conditional fieldsIf Student is chosen the system shall show an optional matric-number field; if Indigene is chosen it shall show a required community list (Akungba, Iwaro, Etioro, Ayegunle, Oke-Oka, Other).H
FR-05Anonymous reportingThe system shall let the reporter tick "Report anonymously"; the name and contact fields shall then be hidden and shall not be stored.H
FR-06Issue detailsThe system shall capture category, severity (Low, Medium, High, Emergency), location, incident date, short title and description.H
FR-07ValidationThe system shall reject a report and show a clear message if a required field is empty, the date is in the future, the title is shorter than 5 characters, the description is shorter than 20 characters, or a contact given is not a valid phone number or e-mail.H
FR-08Ticket generationOn a valid submission the system shall create a unique ticket ID of the form IRO-YY-XXXXX (no ambiguous characters 0, O, 1, I) and set status to Submitted.H
FR-09ConfirmationThe system shall display the ticket ID with a link to track the report.H
4.3 Tracking
FR-10Track by ticketThe system shall let anyone enter a ticket ID (case-insensitive) and view the report's title, category, severity, date, current status and status history with notes.H
FR-11Privacy on trackingThe tracking page shall not display the reporter's name, contact, matric number or description.H
FR-12Unknown ticketIf no report matches, the system shall show "No report found with that ticket ID".H
4.4 Desk officer (administration)
FR-13LoginThe admin desk shall be accessible only after a correct passcode is entered; the session ends on logout or when the browser tab is closed.H
FR-14Dashboard statisticsThe system shall show total reports, open reports, active emergencies and resolved reports.H
FR-15List, search & filterThe system shall list all reports newest first and allow search by ticket ID, title or location, and filtering by status, category and reporter type.H
FR-16View detailsThe system shall show a report's full details, including reporter identity (or "Anonymous") and history.H
FR-17Update statusThe officer shall be able to set a new status with an optional note; the system shall append a timestamped history entry.H
FR-18EscalateThe officer shall be able to mark a report as Escalated with a note naming the authority it was forwarded to.H
FR-19DeleteThe officer shall be able to delete a report after confirming (e.g. spam or duplicates).M
4.5 Future functions
FR-20NotificationsThe system should send SMS/e-mail alerts to reporters who give contact details when status changes.L
FR-21Evidence uploadThe system should allow photo/video attachments.L
FR-22Reports & trendsThe system should produce monthly summaries by category and community.L

5. Non-Functional Requirements

IDAttributeRequirement
5.1 Performance
NFR-01Response timeEach page shall load and become usable within 2 seconds on a 3G mobile connection; form submission and search shall respond within 1 second for up to 1,000 stored reports.
NFR-02Page weightTotal size of the app shall stay under 200 KB, with no external libraries, so it works on low-data plans.
5.2 Security & Privacy
NFR-03ConfidentialityAnonymous reports shall store no name or contact. Identifying data shall be visible only on the admin desk.
NFR-04Access controlAdmin functions shall require authentication. (v1.0 uses a demo passcode; production shall use server-side authentication with hashed passwords and HTTPS.)
NFR-05Input safetyAll user text shall be HTML-escaped before display to prevent script injection (XSS).
NFR-06Ticket secrecyTicket IDs shall be random (325 ≈ 33 million combinations per year) so they cannot easily be guessed.
NFR-07Data protectionHandling of personal data shall comply with the Nigeria Data Protection Act 2023.
5.3 Usability & Accessibility
NFR-08Ease of useA first-time user shall be able to submit a report in under 3 minutes without help.
NFR-09Responsive designThe UI shall work on screens from 320 px (small phones) to desktop without horizontal scrolling.
NFR-10AccessibilityAll inputs shall have visible labels, keyboard focus shall be visible, and text contrast shall meet WCAG 2.1 AA.
NFR-11Clear languageMessages shall be in plain English; Yoruba support is a future enhancement.
5.4 Reliability & Availability
NFR-12Data integrityEvery status change shall be logged; history entries shall never be edited or removed except when the whole report is deleted.
NFR-13Fault toleranceIf stored data is unreadable the system shall start with an empty list rather than crash.
NFR-14AvailabilityWhen hosted, the system shall be available 99% of the time (excluding planned maintenance).
5.5 Maintainability & Portability
NFR-15ModularityAll data access shall go through IssueStore so storage can be replaced without changing UI code.
NFR-16ConfigurabilityCategories, communities, statuses and severities shall be defined in one configuration object (IRO).
NFR-17PortabilityThe app shall run in current versions of Chrome, Firefox, Edge and Safari with no installation.
NFR-18Code qualitySource shall be commented and kept in a public GitHub repository with documentation.
5.6 Social / Ethical
NFR-19NeutralityThe system shall treat students and indigenes equally; the wording of forms shall not blame either group.
